# โครงสร้าง CMS ตกแต่งเว็บไซต์ และแนวทาง Redesign

> เอกสารส่งต่อสำหรับสองทีม: ทีมออกแบบใช้กำหนดหน้าตา Editor ใหม่ ทีมพัฒนาใช้ตั้ง scope ของ POC เนื้อหาตรวจสอบกับซอร์สโค้ดจริงของ ketcms แล้ว ครอบคลุมโครงสร้างปัจจุบัน ช่องว่างที่พบ แกนสถาปัตยกรรม 3 โหมดการแก้ไข ขอบเขตความปลอดภัยของหน้าที่แก้ไขไม่ได้ และแผนแยกหน้าร้านออกเพื่อให้ได้คะแนนความเร็วและการถูกค้นเจอตามเป้า

## 00 · ข้อสรุป

CMS ปัจจุบันมีโครงสร้าง Page → Section → Element ที่ใช้งานได้ดีอยู่แล้ว งานนี้ไม่ใช่การเขียนใหม่ แต่คือการทำให้โครงนั้นเป็นสัญญาที่เครื่องอ่านออก เพื่อให้คนลากวาง เอเจนต์ภายนอก และผู้ช่วยในตัวระบบ แก้หน้าเดียวกันได้โดยไม่ชนกัน

1. แกนกลางคือ Page Schema — JSON ก้อนเดียวต่อหนึ่งหน้า ทุกวิธีแก้ไขเขียนลงก้อนนี้ ทำให้ undo, เวอร์ชัน, พรีวิว และ diff ใช้ร่วมกันได้ทั้งหมด
2. ลากวางยังเป็นทางหลัก — ทุกอย่างที่ผู้ใช้ทำได้วันนี้ต้องทำได้เหมือนเดิมหรือดีกว่า ก่อนจะปล่อยฟีเจอร์ AI ใด ๆ
3. ล็อกด้วยข้อมูล ไม่ใช่ด้วยเงื่อนไขในโค้ด — แต่ละหน้าประกาศระดับล็อก L0–L3 แล้ว Editor กับ API อ่านค่าเดียวกัน เพิ่มหน้าใหม่ไม่ต้องแก้ Editor
4. หน้าธุรกรรมแก้ได้เฉพาะค่า — ตะกร้า ชำระเงิน สมัครสมาชิก โปรไฟล์ ปรับข้อความ ซ่อนฟิลด์ เปลี่ยนสีปุ่มได้ แต่ย้ายหรือลบบล็อกหลักไม่ได้
5. Section AI แบ่งเป็นสองระดับ — ระดับ HTML กับ CSS เป็นค่าเริ่มต้นเพราะยังเก็บ SEO ได้เต็ม ส่วนระดับที่มี JavaScript ต้องอยู่ในกรอบแยกและไม่ถูกจัดทำดัชนี
6. MCP ต่อยอดของเดิม — ระบบมีช่องทางให้ผู้ช่วยภายนอกเชื่อมอยู่แล้ว เพิ่มชุดคำสั่งฝั่งตกแต่งเข้าไป โดยเขียนได้เฉพาะฉบับร่าง
7. ผู้ช่วยในระบบต้องใช้ทางเดียวกับภายนอก — ถ้าเราสร้างทางลัดให้ตัวเอง จะไม่มีวันรู้ว่าชุดคำสั่งที่ปล่อยให้ลูกค้านั้นใช้งานได้จริงหรือไม่
8. เผยแพร่ต้องมีคนกด — ค่าเริ่มต้นให้ทุกการแก้ไขจากผู้ช่วยลงฉบับร่าง แล้วให้คนดูส่วนต่างก่อนขึ้นจริง
9. หน้าร้านแยกออกมาเป็นเทคใหม่ หลังร้านอยู่ที่เดิม — หน้าร้านปัจจุบันวาดด้วยสคริปต์หลังโหลด ทำให้เครื่องมือค้นหาและผู้ช่วยมองไม่เห็นเนื้อหา และคะแนนความเร็วขึ้นไม่ถึงเป้า ย้ายทั้งหมดรวมหน้าตะกร้าและหน้าสมาชิก เพื่อไม่ให้เหลือสองระบบที่ต้องดูแลคู่กันไปตลอด
10. ย้ายการวัดผลโฆษณาก่อนย้ายหน้าร้าน — ถ้าเปลี่ยนสองอย่างพร้อมกันแล้วยอดแปลงตก จะแยกไม่ออกว่าอะไรเป็นสาเหตุ

> อ่านซอร์สโค้ดแล้ว ข้อสรุปข้างบนตรวจสอบกับ ketcms ของจริงแล้ว รายละเอียดสิ่งที่พบและช่องว่างห้าข้อ อยู่ในหัวข้อถัดไป ส่วนที่ยังเหลือคือโครงสร้างตารางฐานข้อมูลฝั่งเซิร์ฟเวอร์ เพราะที่เก็บนี้เป็นฝั่งหน้าจออย่างเดียว

### โครงข้อมูลของบล็อกที่ใช้อยู่

ทุกบล็อกไม่ว่าจะเป็นแถบใหญ่หรือชิ้นย่อย ใช้รูปแบบเดียวกันสามส่วน จุดนี้คือข้อดีที่สุดของระบบเดิม และเป็นเหตุผลว่าทำไมจึงไม่ควรเขียนใหม่

```
{
  "init": {                    ข้อมูลระบุตัวตนและพฤติกรรมในหน้าจอแก้ไข
    "name":         ชื่อที่แสดงในรายการ
    "selector":     ชนิดของบล็อก ใช้เลือกคอมโพเนนต์ที่จะวาด
    "id" / "uid":   ตัวระบุแถวในฐานข้อมูล และตัวระบุชั่วคราวในหน้าจอ
    "enable":       เปิดหรือปิดการแสดงผล
    "have_element": บล็อกนี้รับลูกได้หรือไม่
    "have_setting": มีหน้าต่างตั้งค่าหรือไม่
    "static_page":  ธงล็อก ปัจจุบันติดจากเงื่อนไขตายตัวในหน้าจอ
  },
  "data": {                    ค่าที่ผู้ใช้ตั้ง แตกต่างกันตามชนิดบล็อก
    "fullwidth", "paddingTopBottom", "display_screen", สี ฟอนต์ รูป ...
  },
  "elements": [ ... ]          รายการลูก ใช้โครงเดียวกันซ้อนลงไป
}
```

ข้อเสนอคือเติมสามสิ่งลงในโครงนี้โดยไม่รื้อของเดิม หนึ่งคือชั้นช่องที่บอกว่าตรงไหนเปิดให้แก้ สองคือการอ้างอิงชุดสีกลางแทนค่าสีดิบ สามคือหมายเลขรุ่นของโครงสร้างเพื่อให้ย้ายข้อมูลในอนาคตได้

## D1 · สามโหมดการแก้ไข หนึ่งแกนกลาง

สามวิธีแก้ไขหน้าเว็บไม่ใช่สามระบบ แต่เป็นสามหน้าต่างที่มองเข้าไปยังข้อมูลชุดเดียวกัน จุดที่ทุกอย่างมาบรรจบคือ Design Core API ซึ่งเป็นด่านเดียวที่เขียนลงฉบับร่างได้

**[แผนภาพ D1 สถาปัตยกรรมสามโหมด]** — ดูภาพประกอบในไฟล์ HTML

> ข้อบังคับสำคัญ โหมด C ต้องเรียกผ่านชุดคำสั่งเดียวกับโหมด B ห้ามมีทางลัดภายใน เพราะเป็นวิธีเดียวที่จะพิสูจน์ว่าชุดคำสั่งที่ปล่อยให้ลูกค้าใช้งานได้จริง

## D2 · โครงสร้างเนื้อหา

ลำดับชั้นปัจจุบันชัดเจนอยู่แล้ว สิ่งที่เพิ่มคือชั้น Region ซึ่งเป็นตัวกำหนดว่าตรงไหนของหน้าเปิดให้แก้ และชั้น Token ที่ทำให้สีกับฟอนต์ไหลลงมาจากศูนย์กลางแทนที่จะฝังในแต่ละชิ้น

**[แผนภาพ D2 ลำดับชั้นเนื้อหาและจุดเชื่อม]** — ดูภาพประกอบในไฟล์ HTML

> ชื่อสนามที่ยืนยันแล้วจากโค้ด หน้าหนึ่งมี page_id กับ path และมีข้อมูล SEO แยกสี่ภาษาคือชื่อเรื่อง คำสำคัญ คำอธิบาย และภาพแชร์ พร้อมธงหน้าอ้างอิงหลักและรหัสหน้าที่อ้างถึง ส่วนเมนูมีชนิดสิบแบบ เช่นหน้าปกติ หน้าระบบ สินค้า บทความ หมวดหมู่ ลิงก์ภายนอก ลิงก์ภายใน และหัวข้อ ชั้นช่องเป็นสิ่งที่เสนอเพิ่ม ยังไม่มีในของเดิม ส่วนโครงสร้างตารางฝั่งเซิร์ฟเวอร์ยังต้องขอแยก เพราะที่เก็บนี้เป็นฝั่งหน้าจออย่างเดียว

## D3 · หน้าไหนแก้ได้แค่ไหน

ปัจจุบันระบบแบ่งหน้าเป็นสามกลุ่มคือหน้าที่อยู่บนเมนู หน้าที่ไม่อยู่บนเมนู และหน้าที่ระบบสร้างเอง โดยหน้ากลุ่มหลังถูกทำเครื่องหมายด้วยเงื่อนไขตายตัวสิบห้ากรณีในหน้าจอแก้ไข ข้อเสนอคือย้ายกฎนี้ลงไปเป็นข้อมูลที่เซิร์ฟเวอร์บังคับ และขยายเป็นสี่ระดับ เพราะแก้ไม่ได้เลยกับแก้ได้บางอย่างต่างกันมากในมุมผู้ใช้

| L1 | เฉพาะช่องที่เปิด | ได้ | ได้ทุกระดับ ในช่องที่เปิด | รายละเอียดสินค้า หมวดหมู่ บทความ |
| L2 | ไม่ได้ | ข้อความ ซ่อนฟิลด์ สีปุ่ม | เฉพาะ HTML กับ CSS และเฉพาะช่องท้าย | ตะกร้า ชำระเงิน สมัคร โปรไฟล์ |
| L3 | ไม่ได้ | ไม่ได้ | ไม่ได้ | ผลชำระเงิน ตั้งรหัสผ่านใหม่ |

### รายการที่ถูกล็อกอยู่จริงในวันนี้

สิบห้ากรณีที่หน้าจอแก้ไขไล่เทียบอยู่ ทั้งหมดถูกจัดเป็นล็อกแบบเดียวกันหมด ไม่มีระดับกลาง งานแรกคือแมปรายการนี้เข้ากับสี่ระดับข้างบน แล้วย้ายไปเก็บเป็นข้อมูลฝั่งเซิร์ฟเวอร์

| กลุ่ม | ชนิดบล็อกที่ถูกล็อก | ระดับที่เสนอ |
|---|---|---|
| บัญชีและสมาชิก | เข้าสู่ระบบ · สมัครสมาชิก · โปรไฟล์ · ประวัติการสั่งซื้อ | L2 |
| ธุรกรรม | ยืนยันคำสั่งซื้อ · แจ้งชำระเงิน · ติดตามพัสดุ | L2 |
| ปลายทาง | ขอบคุณ · ได้รับการแจ้งชำระเงินแล้ว | L3 |
| รายการเนื้อหา | รายการสินค้า · รายการบทความ · สินค้าตามป้าย · บทความตามป้าย | L1 |
| รายละเอียด | รายละเอียดสินค้า · รายละเอียดบทความ | L1 |

สังเกตว่าห้ารายการล่างสุดคือหน้าที่ลูกค้าอยากแต่งมากที่สุด แต่วันนี้ถูกล็อกเท่ากับหน้าชำระเงิน การแยกเป็นสี่ระดับจึงปลดล็อกคุณค่าให้ลูกค้าได้ทันทีโดยไม่ลดความปลอดภัย

## D4 · ผังหน้าจอ Editor

ผังนี้คือจุดตั้งต้นสำหรับทีมออกแบบ ไม่ใช่ข้อบังคับเรื่องหน้าตา แต่เป็นรายการงานที่หน้าจอต้องรองรับ ทุกช่องมีเหตุผลเชิงโครงสร้างรองรับจาก D2 และ D3

**[แผนภาพ D4 ส่วนประกอบหน้าจอและหน้าที่ของแต่ละช่อง]** — ดูภาพประกอบในไฟล์ HTML

> ข้อจำกัดเชิงเทคนิคที่กระทบการออกแบบ การลากข้ามขอบ iframe จากแถบซ้ายเข้าผืนผ้าใบทำได้ยากและเปราะ จึงเสนอให้ใช้รูปแบบเลือกจากคลังก่อนแล้วจึงเลือกตำแหน่งวาง

## D5 · Section AI และกรอบความปลอดภัย

การให้ผู้ช่วยเขียนโค้ดได้อิสระคือสิ่งที่ทำให้หน้าเว็บสวยได้จริง แต่ก็เปิดความเสี่ยงสามอย่างพร้อมกันคือสคริปต์อันตราย สไตล์รั่วไปทั้งเว็บ และเนื้อหาที่เครื่องมือค้นหาอ่านไม่เห็น จึงเสนอให้แบ่งเป็นระดับแล้วให้ระดับที่ปลอดภัยกว่าเป็นค่าเริ่มต้น

| ระดับ | ให้เขียนอะไร | กรอบจำกัด | เก็บดัชนีได้ | ใช้ได้ที่ |
|---|---|---|---|---|
| T0 | ไม่เขียนโค้ด ประกอบจาก Section และ Element ที่มี | ไม่ต้องมี | ได้เต็ม | ทุกหน้า เป็นค่าตั้งต้น |
| T1 | HTML กับ CSS | กรองแท็กตามรายการอนุญาต จำกัดขอบเขต CSS ให้อยู่ใน Section ตัวเองอัตโนมัติ | ได้เต็ม | L0 · L1 · ช่องท้ายของ L2 |
| T2 | เพิ่ม JavaScript | อยู่ในกรอบแยก ไม่แชร์โดเมน ไม่เห็นคุกกี้ คุยผ่านช่องทางแคบ | ไม่ได้ | L0 · L1 เท่านั้น |

> สิ่งที่ต้องบอกลูกค้าตรง ๆ เนื้อหาที่ต้องการให้ค้นเจอต้องอยู่ที่ระดับ T1 ส่วน T2 เหมาะกับของที่ต้องโต้ตอบเช่นเครื่องคำนวณหรือแบบทดสอบ ซึ่งไม่ได้ต้องการให้ค้นเจออยู่แล้ว การอธิบายข้อนี้ในหน้าจอตอนเลือกระดับ จะลดปัญหาปลายทางได้มาก

### ด่านตรวจก่อนบันทึก

1. กรองโค้ดอันตรายออก ตามรายการแท็กและคุณสมบัติที่อนุญาต
2. ตรวจว่า CSS ไม่แตะตัวเลือกระดับเว็บ เช่นรากเอกสาร ตัวเนื้อหา หรือคลาสของธีม
3. ตรวจว่าใช้ค่าจากชุดสีกลาง ไม่ใช่ค่าสีดิบที่พิมพ์เอง
4. ตรวจลำดับหัวข้อและคำอธิบายรูป ไม่ให้เสียโครงสร้างการอ่าน
5. ตรวจน้ำหนักไฟล์และผลต่อความเร็วการโหลด
6. ตรวจว่าไม่ได้เขียนลงช่องที่ล็อกไว้

ด่านนี้ใช้ร่วมกันทั้งสามโหมด ไม่ว่าคนเป็นคนวางหรือผู้ช่วยเป็นคนวาง

## D6 · ชุดคำสั่งสำหรับผู้ช่วยภายนอก

ระบบมีช่องทางให้ลูกค้าเชื่อมผู้ช่วยเข้ามาอยู่แล้ว งานนี้คือเพิ่มชุดคำสั่งฝั่งตกแต่งเข้าไปในช่องทางเดิม หลักสำคัญคืออ่านให้ครบก่อน แล้วค่อยเปิดให้เขียน

**[แผนภาพ D6 เส้นทางการทำงานของผู้ช่วยภายนอก]** — ดูภาพประกอบในไฟล์ HTML

> ข้อควรระวังเรื่องต้นทุน ถ้าคำสั่งอ่านหน้าคืนเอกสารทั้งก้อนทุกครั้ง ลูกค้าจะใช้โควตาหมดเร็วมาก ต้องออกแบบให้อ่านเฉพาะส่วนได้ตั้งแต่รอบแรก

## D7 · ชั้นเรนเดอร์และความเร็ว

หลังร้านอยู่กับ Angular ต่อได้ แต่หน้าร้านต้องแยกออกมาเป็นเทคใหม่ เพราะหน้าร้านปัจจุบันวาดด้วยจาวาสคริปต์ทั้งหมดหลังโหลด ทำให้เครื่องมือค้นหาและผู้ช่วยปัญญาประดิษฐ์ที่ไม่รันสคริปต์มองไม่เห็นเนื้อหา และคะแนนความเร็วบนมือถือขึ้นไม่ถึงเป้า

### ทำไมไม่เลือกวาดฝั่งเซิร์ฟเวอร์บนของเดิม

- รุ่นที่ใช้อยู่เก่ากว่ารุ่นที่รองรับการวาดฝั่งเซิร์ฟเวอร์สมัยใหม่อยู่เก้ารุ่นใหญ่ การไล่อัปเกรดมีขนาดงานพอกับการเขียนหน้าร้านใหม่
- ถึงอัปเกรดแล้ว น้ำหนักจาวาสคริปต์พื้นฐานยังสูงกว่าทางเลือกอื่นมาก ซึ่งกินคะแนนหมวดเวลาที่หน้าเว็บไม่ตอบสนอง ที่มีน้ำหนักสามในสิบของคะแนนรวมบนมือถือ
- เมื่อต้องจ่ายค่าย้ายก้อนใหญ่อยู่แล้ว ควรจ่ายไปกับเทคที่ชนะเรื่องนี้โดยตรง

### ขอบเขตใหม่

ตัดสินใจย้ายหน้าร้านทั้งหมด ไม่ใช่เฉพาะหน้าที่ต้องการการค้นเจอ เพราะถ้าเหลือหน้าตะกร้าและหน้าสมาชิกไว้ที่ของเดิม จะกลายเป็นสองระบบที่ต้องแก้ปัญหาเดียวกันสองที่ตลอดอายุการใช้งาน

**[แผนภาพ D7 การแบ่งงานระหว่างของเดิมกับของใหม่]** — ดูภาพประกอบในไฟล์ HTML

> ข้อดีของการย้ายทีละเส้นทางคือของเดิมกับของใหม่อยู่ร่วมกันได้ตลอดช่วงเปลี่ยนผ่าน ไม่ต้องสลับทั้งระบบพร้อมกัน และถอยกลับได้ทันทีถ้าเส้นทางไหนมีปัญหา

### เลือกเทคอย่างไร

เมื่อขอบเขตรวมหน้าตะกร้าและหน้าชำระเงินเข้ามาด้วย ตัวเลือกที่เน้นเนื้อหาล้วนจะไม่พอ เพราะการชำระเงินหลายขั้นตอนที่ต้องส่งสถานะข้ามหน้าเป็นงานแบบแอปพลิเคชัน ถ้าฝืนใช้จะจบที่ต้องมีแอปแยกอีกตัว ซึ่งคือปัญหาสองระบบแบบเดิมที่ต้องการเลี่ยง

| ตัวเลือก | เพดานคะแนนความเร็ว | เหมาะเมื่อ | ข้อเสีย |
|---|---|---|---|
| แบบผสมสองโหมดในโครงเดียว เป็นข้อเสนอ | ถึงเป้าได้ ต้องออกแรงเรื่องน้ำหนักสคริปต์ | มีทั้งหน้าเนื้อหาและหน้าแบบแอปในระบบเดียว ตรงกับขอบเขตที่ตกลงกัน | ต้องคุมวินัยเรื่องน้ำหนักสคริปต์อย่างเข้มงวด |
| แบบเน้นเนื้อหาล้วน | สูงสุด ส่งสคริปต์เป็นศูนย์ได้ | ถ้าย้ายเฉพาะหน้าเนื้อหา ไม่รวมหน้าธุรกรรม | หน้าธุรกรรมต้องแยกไปอีกระบบ ขัดกับเป้าหมายลดภาระดูแล |
| แบบทดลองรุ่นใหม่ | ทฤษฎีดีที่สุด | โครงการทดลอง | ระบบนิเวศเล็ก เสี่ยงเกินไปสำหรับแพลตฟอร์มที่มีลูกค้าจริง |

### เป้าหมายคะแนนและสิ่งที่การันตีได้จริง

> คะแนนเกินเก้าสิบทุกร้านการันตีไม่ได้ เพราะร้านอัปภาพปกขนาดใหญ่มากและติดสคริปต์ภายนอกเองได้ สิ่งที่การันตีได้มีสามอย่าง หนึ่งคือคะแนนพื้นฐานของแพลตฟอร์มบนหน้าเปล่า สองคือระบบที่กันไม่ให้ร้านทำพังโดยไม่รู้ตัว สามคือการแจ้งเตือนเมื่อคะแนนของร้านตก

น้ำหนักคะแนนบนมือถือกระจุกอยู่ที่สามหมวด คือเวลาที่หน้าไม่ตอบสนองสามในสิบ เวลาที่เนื้อหาหลักปรากฏสองจุดห้าในสิบ และการกระโดดของเลย์เอาต์อีกสองจุดห้าในสิบ รวมแปดในสิบอยู่ที่การทำงานของสคริปต์และการขยับของหน้า ไม่ใช่แค่ความเร็วเซิร์ฟเวอร์

#### ห้าเรื่องที่ตัดสินผลจริง เรียงตามผลกระทบ

1. สคริปต์จากภายนอก ระบบรองรับตัววัดผลและแชตจากหลายเจ้า ร้านจริงติดกันสี่ถึงหกตัว นี่คือความต่างระหว่างคะแนนห้าสิบกับเก้าสิบ ทางแก้คือย้ายการวัดผลไปทำฝั่งเซิร์ฟเวอร์ ส่วนที่เหลือให้โหลดช้าลงจนกว่าผู้ใช้จะมีปฏิสัมพันธ์
2. ฟอนต์ไทย ใหญ่กว่าฟอนต์ละตินสองถึงสี่เท่าและเป็นต้นเหตุหลักของการกระโดด ทางแก้คือเก็บไว้ที่เซิร์ฟเวอร์ตัวเอง ตัดเฉพาะอักขระที่ใช้ โหลดล่วงหน้าเฉพาะตัวที่ใช้กับเนื้อหาหลัก และปรับขนาดฟอนต์สำรองให้ตรงกันเพื่อไม่ให้หน้าขยับตอนสลับ จำกัดไม่เกินสองตระกูล
3. รูปภาพ ต้องบังคับที่สายการผลิต ไม่ใช่ขอความร่วมมือจากผู้ใช้ แปลงรูปแบบอัตโนมัติ เตรียมหลายขนาด บังคับให้ทุกรูปมีความกว้างและความสูงเพื่อกันหน้าขยับ และให้รูปหลักโหลดก่อน ที่เหลือโหลดเมื่อเลื่อนถึง
4. โควตาสคริปต์ต่อบล็อก แต่ละบล็อกประกาศสคริปต์ที่ตัวเองต้องใช้ แล้วโหลดเมื่อเลื่อนถึงเท่านั้น บล็อกที่ไม่มีปฏิสัมพันธ์ต้องไม่ส่งสคริปต์เลย
5. บังคับด้วยระบบตรวจอัตโนมัติ วัดคะแนนห้าหน้าตัวแทนทุกครั้งที่จะรวมโค้ด และไม่ให้ผ่านถ้าต่ำกว่าเก้าสิบสอง เผื่อระยะไว้เหนือเป้าสองคะแนน

### ได้เรื่องการถูกผู้ช่วยค้นเจอมาด้วย

ผู้ช่วยปัญญาประดิษฐ์ที่ไปเก็บข้อมูลเว็บส่วนใหญ่ไม่รันสคริปต์ หน้าร้านแบบปัจจุบันจึงมองไม่เห็นเนื้อหาเลย ไม่ใช่แค่เครื่องมือค้นหาที่เสียประโยชน์ เมื่อย้ายมาวาดฝั่งเซิร์ฟเวอร์แล้ว เติมอีกสามอย่างจะครบชุด

- ข้อมูลโครงสร้างที่สร้างจากชนิดบล็อกในหน้า แทนการประกาศเป็นบทความข่าวเหมือนกันหมดอย่างที่เป็นอยู่ หน้าสินค้าออกข้อมูลสินค้าและราคาและคะแนนรีวิว หน้าคำถามออกข้อมูลคำถาม บทความออกข้อมูลบทความ แล้วรวมเป็นก้อนเดียวต่อหน้า
- ไฟล์แนะนำเนื้อหาสำหรับผู้ช่วย และช่องทางดึงข้อความสะอาดต่อหน้า
- ชุดสีและฟอนต์ฝังเป็นตัวแปรในส่วนหัวของเอกสาร เร็วกว่าเดิมและปิดช่องโหว่การสั่งรันข้อความโค้ดไปในตัว

## D8 · การวัดผลโฆษณาระหว่างย้ายระบบ

ความเสี่ยงข้อนี้สูงกว่างานความเร็ว เพราะถ้าพลาดแล้วตัวเลขเพี้ยน ลูกค้าจะยิงโฆษณาผิดทิศและเสียเงินจริง โดยรู้ตัวช้า

### ห้าอาการที่พังแบบเงียบ

| ความเสี่ยง | สิ่งที่เกิดขึ้น |
|---|---|
| นับการซื้อซ้ำ ลูกค้ารีเฟรชหน้าขอบคุณหรือกดย้อนกลับ | ยอดแปลงเกินจริง ผลตอบแทนโฆษณาดูสวยเกินจริง นำไปสู่การเพิ่มงบผิดช่องทาง |
| การซื้อหายไป การส่งกลับจากผู้ให้บริการชำระเงินไม่สำเร็จ หรือลูกค้าปิดหน้าก่อนถึงหน้าขอบคุณ | ยอดแปลงขาด และถ้าเกิดพร้อมกับการย้ายหน้าร้าน จะแยกไม่ออกว่าเว็บแย่ลงหรือการวัดผลพัง |
| นับซ้ำระหว่างฝั่งเบราว์เซอร์กับฝั่งเซิร์ฟเวอร์ | ตัวเลขเป็นสองเท่าทันทีถ้าไม่มีรหัสเหตุการณ์ร่วมให้แพลตฟอร์มรวมให้ |
| เหตุการณ์หายตอนเปลี่ยนรูปแบบการโหลดหน้า เดิมยิงตอนเปลี่ยนเส้นทางในหน้าเดียว ของใหม่เป็นการโหลดหน้าใหม่ | เส้นทางการซื้อขาดเป็นช่วง หาสาเหตุยากเพราะไม่มีข้อผิดพลาดใดปรากฏ |
| คำสั่งซื้อจากหน้าร้านจริง ตลาดกลาง และลิงก์ปิดการขาย หลุดเข้าไปในตัววัดผลโฆษณา | อันตรายที่สุด เพราะผลตอบแทนโฆษณาพองขึ้นและดูเหมือนโฆษณาได้ผลดีขึ้น ทั้งที่ยอดนั้นไม่ได้มาจากโฆษณา |

> ข้อสุดท้ายขอเน้น ตอนย้ายไปยิงจากฝั่งเซิร์ฟเวอร์ จะล่อใจมากที่จะยิงจากเหตุการณ์สร้างคำสั่งซื้อโดยตรง ห้ามทำ ต้องกรองเฉพาะคำสั่งซื้อที่มาจากช่องทางเว็บเท่านั้น

### ทางออกคือชั้นกลางชั้นเดียว

แอปยิงเหตุการณ์ครั้งเดียว แล้วให้ชั้นกลางกระจายออกไปทั้งฝั่งเบราว์เซอร์และฝั่งเซิร์ฟเวอร์ โดยแนบรหัสเหตุการณ์เดียวกันไปทั้งสองทาง แพลตฟอร์มปลายทางจะรวมให้เองและไม่นับซ้ำ

**[แผนภาพ D8 ชั้นกลางสำหรับกระจายเหตุการณ์]** — ดูภาพประกอบในไฟล์ HTML

> การย้ายมาวัดผลฝั่งเซิร์ฟเวอร์ไม่ใช่งานเทคนิคอย่างเดียว แต่เป็นสิ่งที่ขายลูกค้าได้ เพราะแก้ปัญหาการวัดผลที่หายไปจากข้อจำกัดของเบราว์เซอร์ ทำให้ตัวเลขแม่นขึ้นพร้อมกัน

### สิ่งที่ระดับแพลตฟอร์มต้องคิดเผื่อ

- หลายร้านหลายบัญชีโฆษณา กุญแจเชื่อมต่อของแต่ละเจ้าต้องเก็บแยกรายร้าน เข้ารหัส และมีหน้าจอให้ร้านใส่เอง งานนี้ใหญ่กว่าที่คิดเมื่อมีผู้เช่าหลายราย
- ความยินยอมและกฎหมายคุ้มครองข้อมูล ต้องส่งสถานะความยินยอมครบทุกหมวด และฝั่งเซิร์ฟเวอร์ต้องเคารพความยินยอมด้วย ไม่ใช่ยิงทะลุเพราะไม่ผ่านเบราว์เซอร์
- การจับคู่ผู้ใช้ให้แม่นขึ้น ส่งอีเมลและเบอร์โทรแบบเข้ารหัสทางเดียวจะเพิ่มอัตราการจับคู่ได้มาก แต่ต้องอยู่ใต้ความยินยอมเสมอ

### ลำดับการย้ายที่ปลอดภัย

> กฎเหล็ก ห้ามเปลี่ยนหน้าร้านกับเปลี่ยนการวัดผลพร้อมกัน ถ้ายอดแปลงตกสองส่วนในสิบ จะไม่มีทางรู้ว่าเว็บแย่ลงหรือการวัดผลพัง แล้วจะเสียเวลาไล่หาเป็นเดือน

| ขั้น | ทำอะไร | ทำบนอะไร |
|---|---|---|
| 0 | ติดตั้งชั้นกลางใหม่ ยิงคู่ไปยังบัญชีสำรองเพื่อเทียบตัวเลข | เว็บเดิม |
| 1 | เปิดฝั่งเซิร์ฟเวอร์แบบยังไม่นับจริง ส่งเข้าโหมดทดสอบ แล้วเทียบกับฝั่งเบราว์เซอร์ | เว็บเดิม |
| 2 | ปรับจนตัวเลขสองฝั่งต่างกันไม่เกินสองในร้อย แล้วสลับเป็นของจริง | เว็บเดิม |
| 3 | การวัดผลนิ่งแล้ว จึงเริ่มย้ายหน้าร้าน | เริ่มของใหม่ |

ขั้นศูนย์ถึงสองให้ผลทางธุรกิจทันทีโดยยังไม่ต้องแตะหน้าร้านเลย จึงขออนุมัติงบภายในได้ง่ายกว่า และเป็นเหตุผลที่ควรเริ่มงานนี้ขนานไปกับงานฐานสามสัปดาห์แรก

## B1 · โจทย์สำหรับทีมออกแบบ

ส่วนนี้คัดลอกไปใช้เป็นโจทย์ตั้งต้นได้เลย เนื้อหาอ้างอิงจาก D3 และ D4

> **ออกแบบหน้าจอ Editor ใหม่ของ Ketshopweb CMS โจทย์สำหรับงานออกแบบ**

#### สิ่งที่กำลังออกแบบ

หน้าจอแต่งเว็บไซต์ในระบบหลังร้านของแพลตฟอร์มอีคอมเมิร์ซไทย ผู้ใช้คือเจ้าของร้านและทีมการตลาด ส่วนใหญ่ไม่ใช่นักออกแบบและไม่เขียนโค้ด หลายคนทำงานบนแล็ปท็อปจอเล็กหรือแท็บเล็ต ผืนผ้าใบตรงกลางจะเป็นหน้าพรีวิวของหน้าร้านจริงที่ฝังเข้ามา ไม่ใช่ภาพจำลอง จึงต้องออกแบบตัวจับลากและกรอบการเลือกให้อ่านออกเมื่อวางทับเนื้อหาจริงที่มีสีพื้นหลากหลาย

#### งานที่ผู้ใช้มาทำบ่อยที่สุด

1. เปลี่ยนแบนเนอร์หน้าแรกก่อนแคมเปญ
2. เพิ่มบล็อกสินค้าแนะนำ แล้วย้ายตำแหน่ง
3. แก้ข้อความและรูปในบล็อกที่มีอยู่
4. ดูว่าหน้าตาบนมือถือเป็นอย่างไร
5. ย้อนกลับเมื่อแก้แล้วไม่ถูกใจ

#### ปัญหาที่ต้องแก้ให้ได้

- ผู้ใช้ไม่รู้ว่าตรงไหนแก้ได้ ตรงไหนแก้ไม่ได้ จนกว่าจะลองแล้วล้มเหลว
- หน้าตะกร้าและหน้าสมัครสมาชิกแก้ได้เพียงบางอย่าง แต่หน้าจอไม่เคยบอกล่วงหน้าว่าอย่างไหนได้
- เมื่อผู้ช่วยสร้างบล็อกให้ ผู้ใช้ต้องรู้ว่าอะไรเปลี่ยนไปบ้างก่อนจะยอมรับ

#### หน้าจอและสถานะที่ต้องออกแบบ

- หน้าเลือกหน้าเว็บที่จะแต่ง แยกสามกลุ่มคือหน้าบนเมนู หน้านอกเมนู และหน้าของระบบ
- หน้าจอหลักสามช่อง คือชั้นของหน้าและคลังทางซ้าย ผืนผ้าใบตรงกลาง คุณสมบัติทางขวา
- สถานะขณะลาก ทั้งเงาของสิ่งที่ลาก เส้นบอกตำแหน่งวาง และการเลื่อนหน้าอัตโนมัติเมื่อลากถึงขอบ
- สถานะเมื่อวางในที่ที่ล็อก ต้องบอกเหตุผลและบอกว่าวางตรงไหนได้แทน
- สี่ระดับการล็อก L0 ถึง L3 ต้องมองออกทันทีจากผืนผ้าใบโดยไม่ต้องคลิก
- แผงคุณสมบัติที่แยกให้เห็นว่าค่าไหนสืบทอดมาจากชุดสีกลาง ค่าไหนถูกตั้งทับเฉพาะจุดนี้
- แผงผู้ช่วย พร้อมมุมมองส่วนต่างที่ยอมรับได้ทีละจุด
- สถานะว่างเปล่า เช่นหน้าที่ยังไม่มีบล็อก และสถานะข้อผิดพลาดจากด่านตรวจ
- สลับมุมมองคอมพิวเตอร์ แท็บเล็ต มือถือ ภายในผืนผ้าใบ
- ไทม์ไลน์ประวัติเวอร์ชันและการย้อนกลับ

#### ข้อบังคับ

- ทุกการกระทำต้องทำด้วยคีย์บอร์ดได้ ผู้ใช้จำนวนมากทำงานบนแท็บเล็ตที่ลากยาก
- ผืนผ้าใบต้องได้พื้นที่มากที่สุดเสมอ แผงข้างยุบได้
- สีแดงใช้สื่อความหมายว่าล็อกหรืออันตราย จึงห้ามใช้เป็นสีตกแต่งทั่วไป
- รองรับภาษาไทยเป็นหลัก ข้อความไทยยาวกว่าอังกฤษราวหนึ่งเท่าตัว เผื่อพื้นที่ให้พอ
- รองรับโหมดสว่างและมืด

#### สิ่งที่อยากได้กลับมา

ผังหน้าจอความละเอียดปานกลางของหน้าจอหลัก พร้อมชุดสถานะการลากวางและการล็อก และแนวทางการสื่อสารว่าอะไรแก้ได้แก้ไม่ได้ ยังไม่ต้องลงรายละเอียดสีและฟอนต์ในรอบแรก

## B2 · ขอบเขต POC และแผนย้ายระบบ

แบ่งเป็นสองส่วน ส่วนแรกคือ POC สามสัปดาห์ที่เริ่มได้ทันทีโดยยังไม่ต้องเคาะเรื่องเทคหน้าร้าน ส่วนที่สองคือแผนย้ายเต็มรูปแบบ

**สิ่งที่ต้องพิสูจน์** — หนึ่ง หน้าเดิมแปลงเป็น Page Schema แล้วเรนเดอร์ออกมาเหมือนเดิมได้ สอง ลากวางบนโครงใหม่ทำได้ลื่นเท่าของเดิม สาม การล็อกที่อ่านจากข้อมูลกันการแก้ผิดที่ได้จริงทั้งจากคนและจากผู้ช่วย
**ไม่อยู่ใน POC** — ระบบสิทธิ์เต็มรูปแบบ หลายภาษา ประสิทธิภาพระดับใช้งานจริง และการย้ายข้อมูลลูกค้าเดิม
**หน้าที่ใช้ทดสอบ** — สามหน้าพอ คือหน้าแรกแทน L0 รายละเอียดสินค้าแทน L1 และตะกร้าแทน L2 สามหน้านี้ครอบคลุมทุกกรณีสำคัญ
**ระยะเวลาที่เสนอ** — สามสัปดาห์ ทีมสองถึงสามคน

### ลำดับงาน

| สัปดาห์ | งาน | วัดผลอย่างไร |
|---|---|---|
| 1 | ย้ายกฎการล็อกจากเงื่อนไขตายตัวในหน้าจอ ไปเป็นข้อมูลที่เซิร์ฟเวอร์บังคับ และแยกฉบับร่างออกจากฉบับจริง สองอย่างนี้คือรากของปัญหาทุกข้อ | เรียกบริการบันทึกตรงโดยข้ามหน้าจอ แล้วพยายามแก้บล็อกหลักของหน้าตะกร้า ต้องถูกปฏิเสธจากเซิร์ฟเวอร์ · บันทึกแล้วของจริงยังไม่เปลี่ยนจนกว่าจะสั่งเผยแพร่ |
| 2 | ปรับหน้าจอแก้ไขให้อ่านระดับล็อกจากข้อมูลแทนเงื่อนไขตายตัว แสดงสี่ระดับให้เห็นบนผืนผ้าใบ และเพิ่มปุ่มเผยแพร่พร้อมมุมมองส่วนต่าง | ทำรายการงานเดิมครบทุกข้อบนหน้าแรก · หน้าสินค้าแทรกบล็อกในช่องที่เปิดได้แต่ย้ายบล็อกหลักไม่ได้ · เพิ่มหน้าใหม่เข้าระดับล็อกได้โดยไม่แก้โค้ดหน้าจอ |
| 3 | ชุดคำสั่งสำหรับผู้ช่วย เฉพาะอ่านและเขียนฉบับร่าง ใช้ด่านตรวจเดียวกับสัปดาห์แรก พร้อมแปลงชุดสีจากข้อความโค้ดให้เป็นข้อมูลที่เครื่องอ่านได้ | ต่อผู้ช่วยภายนอกแล้วสั่งเพิ่มบล็อกลงหน้าแรกได้ · สั่งแก้บล็อกหลักของหน้าตะกร้าแล้วถูกปฏิเสธพร้อมเหตุผลที่บอกช่องที่เขียนได้ · ผู้ช่วยอ่านชุดสีของร้านออก |

### แผนย้ายระบบเต็มรูปแบบ

### ข้อเสนอเชิงเทคนิค

- ไม่ต้องเขียนใหม่ ของเดิมเป็น Angular รุ่นใหม่อยู่แล้ว ไม่ใช่รุ่นเก่าอย่างที่เคยเข้าใจ จึงต่อยอดบนโครงเดิมได้ ไม่ต้องย้ายทีละส่วนและไม่ต้องทำหน้าต่างแยก
- การล็อกต้องบังคับที่เซิร์ฟเวอร์ หน้าจอแสดงผลตามเท่านั้น ถ้ายังบังคับที่หน้าจออย่างเดียว การเปิดช่องทางให้ผู้ช่วยเท่ากับเปิดให้แก้หน้าชำระเงินโดยไม่มีอะไรกั้น
- ไลบรารีลากวางเดิมใช้ต่อได้ รองรับการสัมผัสอยู่แล้ว สิ่งที่ต้องเพิ่มคือการทำงานด้วยคีย์บอร์ดและการวาดเฉพาะส่วนที่มองเห็นเมื่อหน้ายาว
- บล็อกต้องเขียนที่เดียว หน้าจอแก้ไขฝังหน้าพรีวิวของหน้าร้านใหม่เข้ามาแทนการวาดเอง ถ้าพลาดข้อนี้จะต้องเขียนบล็อกทุกชนิดสองครั้ง ซึ่งเป็นความเสี่ยงที่ทำให้โครงการล้มได้
- แยกโหมดตามชนิดหน้า หน้าเนื้อหาวาดล่วงหน้าและแคชเพื่อไล่คะแนนความเร็ว ส่วนหน้าธุรกรรมทำงานในเบราว์เซอร์และประกาศไม่ให้เก็บดัชนี จึงไม่ดึงคะแนนเฉลี่ยลง แต่ยังใช้คอมโพเนนต์และชุดสีชุดเดียวกัน
- หน้าบ้านเรนเดอร์ฝั่งเซิร์ฟเวอร์ เพื่อให้เก็บดัชนีได้เต็ม พร้อมสร้างข้อมูลโครงสร้างตามชนิดของ Section โดยอัตโนมัติ เช่นบล็อกสินค้าออกข้อมูลสินค้าและราคา บล็อกคำถามที่พบบ่อยออกข้อมูลคำถาม
- ชุดสีและฟอนต์เก็บเป็นตัวแปรกลาง แล้วให้ทุกชิ้นอ้างถึง ส่วนการเขียนสไตล์เองย้ายมาเป็นทางออกฉุกเฉินที่จำกัดขอบเขตต่อบล็อก แทนที่จะมีผลทั้งเว็บ

### ความเสี่ยงที่ควรพูดคุยตั้งแต่แรก

1. ชุดสีที่เก็บเป็นข้อความโค้ดแล้วสั่งรัน ต้องแปลงเป็นข้อมูลก่อนจึงจะทำระบบอ้างอิงสีกลางได้ ระหว่างแปลงต้องรองรับของเดิมไปพร้อมกัน และเป็นการปิดช่องโหว่ไปในตัว
2. สไตล์ที่ลูกค้าเขียนเองไว้เดิมจะพัง เมื่อโครงสร้างหน้าเปลี่ยน ควรมีโหมดเข้ากันได้กับของเดิมและช่วงที่วาดคู่กันไปก่อน
3. ต้นทุนการเรียกใช้ของลูกค้า ถ้าอ่านหน้าทั้งก้อนทุกครั้ง โควตาจะหมดเร็ว ต้องออกแบบให้อ่านเฉพาะส่วนตั้งแต่ต้น
4. ตัวเลขการวัดผลโฆษณาเพี้ยนระหว่างย้าย ความเสี่ยงสูงกว่างานความเร็ว เพราะกระทบเงินของลูกค้าโดยตรงและรู้ตัวช้า ทางกันคือแยกเวลาให้ชัด ย้ายการวัดผลให้นิ่งก่อนแล้วจึงย้ายหน้าร้าน
5. ขนาดงานย้ายบล็อก เจ็ดสิบสี่รายการในทะเบียนบวกแม่แบบสำเร็จอีกสามสิบแบบ ถ้าทำเรียงทีละอันจะใช้เวลานานเกินไป ควรจัดกลุ่มตามความถี่ที่ลูกค้าใช้จริงแล้วย้ายกลุ่มที่ใช้มากก่อน และเก็บสถิติการใช้งานจริงก่อนเริ่มเพื่อจัดลำดับ
